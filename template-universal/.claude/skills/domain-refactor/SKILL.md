# Domain Refactor

**언제 쓰나:** 도메인 매뉴얼(manual.md)의 규칙에 비춰 실제 코드가 어긋난 곳을 찾을 때. 기본은 진단 전용(report) — 위반 목록과 제안을 리포트로 내고 코드는 건드리지 않는다. 사용자가 "적용/고쳐/apply/수정해줘"라고 명시할 때만 승인된 항목을 규칙 단위로 수정한다. 매뉴얼에 근거가 있는 변경만 하며, 매뉴얼에 없는 개선(성능/스타일 등)은 다루지 않는다. drift_guard 훅이 "검토 필요"를 띄운 도메인에 쓰면 좋다. 매뉴얼이 없으면 먼저 domain-manual을 쓴다.

매뉴얼의 규칙을 기준으로 코드의 어긋남을 찾아 다듬는 스킬. "수집 → 문서화 → 적용 → 감시" 사이클의 **적용** 단계.

핵심 원칙:
1. **기준은 매뉴얼이다.** 매뉴얼의 규칙에 근거가 있는 변경만 한다. 매뉴얼에 없는 개선(성능/스타일/리네이밍)은 범위 밖. 과잉 진단은 신뢰를 깎는다.
2. **진단과 실행을 분리한다.** 기본은 진단 전용. 코드 수정은 사용자가 명시적으로 승인했을 때만.
3. **규칙 단위로, 작게.** 한 규칙의 위반을 묶어 고치고 검증한 뒤 다음 규칙으로. 일괄 대규모 리팩토링 금지.

## 두 가지 모드

- **report (기본):** 위반을 찾아 `docs/domains/<domain>/refactor-report.md`로 낸다. 코드는 건드리지 않는다.
- **apply:** 사용자가 "적용/고쳐/apply"를 명시할 때만. 리포트의 항목 중 사용자가 승인한 것만 규칙 단위로 수정한다. 모드를 임의로 apply로 올리지 않는다.

## 워크플로우

### 1. 매뉴얼 읽기
- 대상 `docs/domains/<domain>/manual.md`를 **Read** 한다.
- `interview_status`가 complete가 아니거나 §7에 미해결 항목이 있으면 경고하고, 그 부분에 해당하는 코드는 점검 대상에서 제외한다 (아직 안 정해진 걸 강제하면 안 됨).
- 점검 대상 섹션: §3 불변 규칙, §4 의존 계약, §2 핵심 모델, §1 책임 범위. (§5/§6/§7은 규칙이 아니므로 점검 안 함.)

### 2. 규칙 → 코드 점검으로 번역
- `references/rule-to-check.md`를 참조해 각 규칙을 "코드에서 무엇을 찾을지"로 바꾼다.
- 매뉴얼 메타블록의 `code_paths` 범위 안에서 Grep/Glob으로 후보를 좁힌다.
- 후보 파일을 Read해 실제 위반인지 확인한다. 정적으로 단정 어려우면 "자동수정 가능: no"로 표시.

### 3. 진단 리포트 생성
- `references/report.template.md`를 채워 `refactor-report.md`로 쓴다 (덮어씀).
- 각 위반은 [근거 규칙 + 매뉴얼 섹션] → [위반 위치] → [현황] → [제안] → [위험도] 형태.
- **매뉴얼에 근거가 없는 항목은 "범위 밖"에 적고 위반으로 올리지 않는다.**
- 이전 리포트가 있으면 위반 수 증감을 요약에 표시한다 (점진적 다듬기 추이).

### 4. (apply 모드일 때만) 승인 후 수정
- 리포트를 사용자에게 보여주고, 어떤 항목을 고칠지 승인받는다. 승인 없이 코드 수정 금지.
- 승인된 항목을 **한 규칙씩** 수정한다. 한 규칙 처리 후:
  - 가능하면 검증을 돌린다 (테스트/타입체크/린트). 깨지면 그 변경을 보류하고 보고.
  - 다음 규칙으로 넘어간다.
- 모든 수정이 끝나면 리포트의 `mode: applied`, `violations_fixed`를 갱신한다.
- 코드를 고쳤으면 매뉴얼의 `last_synced`도 오늘로 갱신해 drift-guard 경고를 정리한다.

## 하지 말 것
- 매뉴얼에 근거 없는 변경을 하지 말 것 — 이 스킬의 범위는 매뉴얼이다.
- 진단만 요청받았는데 코드를 수정하지 말 것.
- 승인 없이 apply하지 말 것. 한 번에 여러 규칙을 몰아 고치지 말 것.
- §7 미해결 항목에 걸린 코드를 "고치지" 말 것 — 아직 결정이 안 됐다.
- 검증이 깨졌는데 밀어붙이지 말 것 — 보류하고 사용자에게 알린다.
