# Code Walkthrough

**언제 쓰나:** 오너가 코드를 **이해**하기 위한 리뷰. 버그를 찾는 게 아니라(그건 /verify),
보안을 보는 것도 아니라(그건 /security-review), "오너가 이 코드를 남에게 설명할 수 있는 상태"를
만드는 것이 목표다. AI가 짠 코드가 쌓이는 속도를 오너의 이해가 따라가지 못하는
이해 부채(comprehension debt)를 줄이는 레이어. `/code-review` 커맨드가 이 방법론을 따른다.

## 산출물 구조 (이 순서 그대로)

### 1. 변경 요약 — 코드 순서가 아니라 의도 순서로
"어떤 결정이 있었고 → 그래서 어떤 파일들이 → 어떤 흐름으로" 순서로 설명한다.
파일 목록부터 나열하지 말 것. 결정이 먼저다.

> 나쁜 예: "auth.py, session.py, middleware.py가 변경됨. auth.py에는..."
> 좋은 예: "세션 만료를 '슬라이딩'으로 정한 결정이 핵심이다. 이 결정이 session.py의
> 갱신 로직을 만들었고, 그걸 매 요청에 적용하려고 middleware.py가 생겼다."

### 2. 읽기 가이드 — 이해하려면 이 순서로 읽어라
진입점 → 핵심 분기 → 데이터가 변하는 지점 순으로, 3~7개 정거장.
각 정거장은 `파일:라인` + 한 문장("여기서 무엇이 결정/변형되는지").
전체 파일을 다 읽으라는 안내는 실패다 — 어디를 안 읽어도 되는지가 정보다.

### 3. 도메인 연결 — 매뉴얼과의 대응
- 이 코드가 `docs/domains/<domain>/manual.md`의 **어떤 불변 규칙/계약을 구현**한 것인지 표로 대응.
- **매뉴얼에 없는 결정이 코드에 들어갔으면 반드시 표면화** — "코드가 X를 가정하는데 매뉴얼엔 없음.
  인터뷰/매뉴얼에 반영할 후보"라고 명시. 이게 drift의 조기 발견이다.
- 도메인 구조가 없는 프로젝트면 이 절은 생략.

### 4. 위험한 곳 — 여기만은 이해하고 넘어가야 한다
나중에 발목 잡을 지점 **2~3곳만**: 암묵적 가정(예: "리스트가 항상 정렬돼 있다고 가정"),
비직관적 처리(예: "빈 배열과 null을 다르게 취급"), 숨은 결합(예: "이 값 바꾸면 저쪽 캐시 무효화 필요").
5곳 이상 나열하면 아무것도 기억 못 한다. 가장 아픈 것만.

### 5. 이해 확인 질문 3개
오너가 답할 수 있어야 하는 질문. 코드를 안 보고 답할 수 있으면 이해한 것이다.
> 예: "로그인 세션이 만료되는 두 가지 경로는?" / "이 API가 404와 403을 나누는 기준은?"

질문 뒤에 답을 바로 쓰지 않는다. 오너가 "답 알려줘"라고 하면 그때 답한다.

## 스타일 규칙

- **구체 라인 인용** — 모든 주장에 `파일:라인`. "대체로", "여기저기" 금지.
- **코드 재나열 금지** — diff를 다시 붙이는 건 설명이 아니다. 코드 조각은 5줄 이하, 꼭 필요할 때만.
- **용어는 CONTEXT.md 기준** — 도메인 용어 사전에 있는 말로 설명. 새 용어를 만들지 말 것.
- **분량** — 요약+가이드+연결+위험+질문 합쳐 화면 1.5장 이내. 길면 이해 도구가 아니라 또 하나의 부채다.
- **대화형** — 산출물을 낸 뒤 오너의 후속 질문("이건 왜 이렇게 했어?")에 이어서 답한다.
  이 문답이 본체이므로, 워크스루는 서브에이전트로 빼지 않고 메인 세션이 직접 수행한다.

## 리뷰 시점 추적

- `docs/reviews/last-review.json`: `{"last_commit": "<sha>", "reviewed_at": "<ISO>", "scope": "<범위>"}`
- 리뷰 범위 기본값: `last_commit..HEAD` diff + 워킹 트리 변경. 파일이 없으면 워킹 트리 diff,
  그것도 비어 있으면 최근 커밋 1개.
- 워크스루 완료 후 last-review.json을 현재 HEAD로 갱신한다.
  다음 리뷰가 "그 이후 쌓인 것"만 잡게 되고, 범위가 크면 이해 부채가 밀렸다는 신호다.
