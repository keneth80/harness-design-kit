## 하네스 규칙

이 프로젝트는 harness-core 플러그인이 켜져 있다. 훅이 규칙을 기계적으로 강제하고, 아래는 사람이 지켜야 할 판단 기준이다.

### 구현 전
- 가정은 밝히고, 불확실하면 묻는다. 해석이 갈리면 임의로 고르지 말고 대안을 제시한다.
- 더 단순한 방법이 있으면 먼저 제안한다.
- 명령을 검증 가능한 목표로 바꾼다. "고쳐줘" → "재현 테스트를 쓰고 통과시킨다".

### 구현 중
- 문제를 푸는 최소한의 코드만 쓴다. 요청하지 않은 기능·추상화·예외 처리는 넣지 않는다.
- 요청과 직접 연결된 줄만 바꾼다. 주변 코드·주석·포맷을 임의로 "개선"하지 않는다.
- 이름은 의도를 드러낸다. Boolean은 is/has/can/should, 이벤트 핸들러는 handle, React hook은 use로 시작한다.
- 주석은 "무엇"이 아니라 "왜"를 쓴다. 임시 코드는 TODO/FIXME로 표시한다.

### 먼저 묻고 할 것
패키지 설치, 아키텍처·스키마·public API 변경, 인증·인가 변경, 배포·환경변수 변경, 보안 로직 변경,
대규모 이동·포맷팅·리팩터링.

### 보안
- 키·토큰·비밀번호는 코드에 쓰지 않는다. 환경변수 이름은 `.env.example`에만 적는다.
- `.env` 같은 시크릿 파일은 읽지 않는다. 하네스가 막으면 우회하지 말고 사용자에게 알린다.
- 실제 개인정보를 예시 데이터로 쓰지 않는다.

### 워크플로우 명령
- `/harness-full:full-cycle` 같은 워크플로우 명령이 "없는 명령"으로 보이면 동적 워크플로우 기능이 꺼진 것이다.
  즉석에서 대신 수행하지 말고, 사용자에게 알리고 `/config`의 Dynamic workflows에서 켤지 묻는다.

### 루프와 통과 판정
- "통과했다"는 판단은 `verify_run.py`가 남긴 원장(`.harness/verify-ledger.json`)의 state로 한다. 말로 통과를 선언하지 않는다.
- 통과시키려고 테스트를 skip하거나 단언을 지우거나 골든 데이터를 고치지 않는다. 테스트가 정말 틀렸으면 근거를 들어 사용자에게 묻는다.

### 끝낼 때
- 편집 후 검증(verify_guard) 경고가 남아 있으면 해결하고 끝낸다.
- 짧게 보고한다: 바꾼 파일 / 주요 변경 / 단순화한 부분 / 알려진 한계 / 다음 추천 작업.

### 참고 파일
- `CONTEXT.md` 도메인 용어 사전. 새 용어가 나오면 추가한다.
- `docs/adr/` 의사결정 기록 (ADR).
- `docs/codemap.md` 자동 생성 코드 지도. 직접 고치지 않는다.
- `docs/domains/` 도메인 인터뷰·매뉴얼. 여기 걸린 코드는 drift_guard가 지킨다.
- `docs/lessons-learned.md`, `docs/error-log.md` 학습 기록. error-curator만 고친다.
