# 결함 체크리스트

시험 범위표와 같다. 과제에 적혀 있지 않아도 채점자는 여기서 낸다. 바뀐 기능마다 해당하는 줄만 보고, 해당하면 **코드와 테스트 둘 다**에 반영한다.
실험(같은 과제를 9번 구현)에서 스스로 검토하지 않은 구현은 아래 3·5·6·7번을 대부분 놓쳤다.

| # | 볼 것 | 흔한 결함 | 테스트 한 줄 예 |
|---|---|---|---|
| 1 | 입력 경계 | 빈 값은 막고 **공백만 있는 값**은 통과, 최대 길이는 생성에만 걸고 수정에는 없음, 숫자 0·음수 | 공백 제목으로 생성·수정 둘 다 거절 |
| 2 | 권한 표 | 리소스 × (주인, 공유·권한 받은 사람, 남, 비로그인) × (읽기, 수정, 삭제, 관리) 중 빈칸 | 칸마다 상태 코드 단언 |
| 3 | 존재 노출 | 남의 리소스에 403을 줘서 있다는 사실을 드러냄 | 남의 것과 없는 것의 응답이 같다 |
| 4 | 필드 끼워 넣기 | 요청 본문의 `owner`, `id`, `role`을 그대로 반영하거나 조용히 무시 (거절이 더 안전) | 정해지지 않은 필드가 오면 거절하고 주인이 바뀌지 않는다 |
| 5 | 경합·정합성 | 조회 후 삽입(check-then-insert)으로 중복 검사, 예외를 잡고 롤백 안 함, 여러 쓰기를 트랜잭션 없이 | 중복 요청이 500이 아니다 |
| 6 | 정수·크기 범위 | 아주 큰 id(2^63 이상)나 아주 긴 본문이 DB·파서에서 터져 500 | 큰 id에 404/422, 큰 본문에 413/422 |
| 7 | 500이 되는 길 | 잘못된 JSON, 타입이 다른 값, null, 빈 본문, 없는 하위 리소스 | 각 입력이 4xx |
| 8 | 연관 데이터 | 삭제 때 공유·첨부·알림이 남음, 사용자 삭제 시 고아 레코드 | 삭제 뒤 다른 사람 목록에서도 사라짐 |
| 9 | 반복 요청 | 같은 요청 두 번(중복 공유, 재시도)이 오류나 중복 레코드 | 두 번 해도 목록에 한 번 |
| 10 | 정보 노출 | 응답·로그에 토큰, 내부 id, 스택 트레이스 | 응답 필드가 계약과 같다 |
| 11 | 범위 이탈 | 요청에 없는 기존 API·규칙 변경 (가입 규칙, 응답 형식, 기본값) | 기존 테스트가 손대지 않고 통과 |
| 12 | 주입 | 문자열로 이어 붙인 SQL·셸·경로 | 따옴표가 든 입력이 그대로 문자열로 처리 |

## 쓰는 법
- **구현 전**: 바뀌는 엔드포인트마다 2번 권한 표를 먼저 채운다. 요청이 정하지 않은 칸은 안전한 쪽(거절, 404)으로 정하고 보고에 적는다.
- **테스트**: 표의 "테스트 한 줄 예"처럼 위험마다 하나씩. 정상 흐름만 여러 개 쓰는 것보다 낫다.
- **검토**: 해당 항목마다 "코드에서 막음 / 테스트 있음"을 확인하고 빠진 것을 지적한다.
- **비례**: 실제 요청으로 재현되는 결함만 고친다. 재현할 수 없는 이론상 문제를 막으려고 핸들러·잠금·검증 계층을 덧붙이지 않는다 (실험에서 검토를 거친 구현은 결함은 줄었지만 과한 방어 코드로 유지보수 점수가 깎였다).
- 프레임워크 기본값을 확인한다 (예: 스키마 검증 라이브러리의 추가 필드 처리, 정수 상한, ORM의 롤백 동작).
