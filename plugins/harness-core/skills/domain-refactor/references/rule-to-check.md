# 규칙 → 코드 점검 매핑

매뉴얼의 자연어 규칙을 코드에서 어떻게 확인하는지에 대한 가이드.
핵심: 매뉴얼 규칙마다 "코드에서 무엇을 찾아볼지"를 도출한다. 매뉴얼에 없는 건 점검하지 않는다.

## 어느 매뉴얼 섹션이 점검 대상인가
- **§3 불변 규칙** → 가장 중요. 각 규칙을 코드 위반으로 번역.
- **§4 의존하는 외부 계약** → 의존 방향/단방향 위반, 소유권 위반 점검.
- **§2 핵심 모델** → 엔티티 제약(필수 필드, 유니크 등)이 코드 모델에 반영됐는지.
- §1 책임 범위 → 이 도메인 코드가 책임 밖 일을 하는지 (월권).
- §5/§6/§7 → 점검 대상 아님(근거/함정/미해결은 규칙이 아님). 단 §7 미해결이 있으면 그 부분은 리팩토링하지 말 것.

## 규칙 유형별 코드 점검 패턴

### 의존 방향 / 단방향 규칙
예: "community는 recommendation_id로 읽기 참조만(단방향)"
→ 코드에서 community 모듈이 recommendation의 쓰기 함수(생성/수정/삭제)를 import/호출하는 곳을 찾는다.
→ Grep: community 디렉터리에서 recommendation의 mutating API 호출.

### 소유권 / 단일 진실 소스 규칙
예: "피부톤 최종 진실은 skin_profile만 소유"
→ skin_profile 외의 도메인이 피부톤을 직접 저장/수정하는 코드를 찾는다.
→ 다른 도메인이 톤을 자체 보관하면 위반.

### 입력 전용 / 비전달 규칙
예: "클라이언트는 톤을 직접 전달하지 않는다. 서버가 skin_profile에서 조회."
→ API 핸들러가 요청 본문에서 톤을 받아 쓰는 코드를 찾는다.

### 모델 제약 규칙
예: "Recommendation 레코드는 불변(immutable)"
→ Recommendation을 생성 후 수정하는(update/save 재호출) 코드를 찾는다.

## 점검 도구
- Grep/Glob으로 후보를 좁힌 뒤, 해당 파일을 Read해 실제 위반인지 확인.
- 정적 패턴만으로 단정 어려운 건 "자동수정 가능: no"로 표시하고 사람 판단에 맡긴다.
- 절대 매뉴얼에 없는 규칙을 상상해 점검하지 않는다. 과잉 진단은 신뢰를 깎는다.
