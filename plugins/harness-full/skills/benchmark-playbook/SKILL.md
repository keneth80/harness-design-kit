# 벤치마크 분석 교본

손님으로 둘러본 기록을 읽고 "이 서비스가 무엇을 하고 어떻게 흐르는가"를 정리한다. 주방(구현)을 추측하는 일이 아니다.

## 입력
- `<사이트 폴더>/site.json`: 페이지마다 제목, 제목 단계(h1~h3), 메뉴, 버튼 문구, 폼 구조, 랜드마크, 개수, 기술 단서, 그리고 사이트 전체의 API 호출 패턴(`api`)과 외부 호스트(`thirdParty`), 건너뛴 주소(`skipped`)
- `<사이트 폴더>/shots/*.png`: 앞쪽 몇 페이지의 데스크톱·모바일 첫 화면. 4장까지만 Read로 본다
- 얕은 모드면 `site.json` 대신 `notes.md` (WebFetch로 본 내용)
- 작업 지시에 들어 있는 "우리 프로젝트" 요약과 "알고 싶은 것"

## 판정
모든 기능과 주장에 셋 중 하나를 붙인다. 모르는 것이 사실처럼 보이지 않게 하는 것이 이 보고서의 핵심이다.
- **확인됨**: 기능이 실제로 있는 화면 요소를 봤다. 폼, 버튼, 그 기능을 쓰는 페이지, 그 기능을 부르는 API 호출 (근거를 적는다)
- **추정**: 메뉴 이름, 소개 문구, 제목, API 경로 이름으로만 짐작했다. "태그로 묶기"라는 소개 제목만 봤다면 추정이다
- **모름**: 로그인 뒤, robots.txt 금지, 페이지 한도 때문에 못 봤다

## 보고서: `<사이트 폴더>/benchmark-report.md`

```
# <호스트> 벤치마크 보고서
둘러본 날: <날짜> · 페이지 <N>쪽 · 건너뜀 <M>개 (robots <a>, 상태 변경 주소 <b>, 한도 <c>)

## 한 줄 요약
<누구에게 무엇을 해 주는 서비스인가>

## 정보 구조
<메뉴 트리. 페이지 경로와 함께>

## 기능 목록
| # | 기능 | 사용자에게 주는 것 | 근거 (페이지·요소) | 판정 |

## 주요 흐름
<첫 방문에서 핵심 행동(가입, 구매, 작성 등)까지 단계별. 각 단계에 근거 페이지>

## 배울 점
<3~7개. 패턴 수준으로: "가격표 바로 아래 FAQ로 망설임을 푼다"처럼. 그대로 옮길 문구나 디자인이 아니라 원리>

## 약점과 빈틈
<접근성(lang, h1, 폼 라벨), 모바일, 빈 상태, 길 잃기 쉬운 곳. 근거와 함께>

## 기술 단서
<프레임워크 단서, 외부 서비스 범주(분석, 결제, 채팅, 지도). 단서일 뿐이라고 적는다>

## 못 본 것
<로그인 뒤 기능, robots.txt 금지 경로, 한도로 멈춘 곳>
```

## 지킬 것
- 보고서 파일 이름은 `benchmark-report.md`로 쓴다. Claude Code는 `report.md`, `summary.md`처럼 이름이 REPORT·SUMMARY·FINDINGS·ANALYSIS로 시작하는 하위 에이전트의 마크다운 쓰기를 막는다.
- 문구는 메뉴·버튼 이름처럼 짧은 것만 인용한다. 본문, 이미지, 로고, 코드는 옮기지 않는다.
- API 경로는 "검색이 있다", "목록을 페이지 단위로 불러온다" 같은 기능 단서로만 쓴다. 내부 구현을 단정하지 않는다.
- "우리 프로젝트" 요약이 있으면 "배울 점"마다 우리에게 맞는지 한 줄을 덧붙인다. 최종 제안은 메인 세션이 사용자와 하니, 여기서는 고르지 않는다.

## 마지막 답변 (메인 세션에 돌려줄 것, 10줄 이내)
보고서 경로, 기능 수(확인됨·추정·모름별), 핵심 흐름 한 줄, 배울 점 상위 3개, 못 본 것 한 줄.
