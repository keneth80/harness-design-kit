# 가정 확인

요즘 모델은 "어떻게 할지"는 잘 정한다. 추측할 수 없는 것은 "무엇을 원하는지"처럼 사용자 머릿속에만 있는 것이다.
그래서 질문 공세 대신, 이해한 것과 할 일을 먼저 보여주고 **틀린 것만** 고쳐 받는다.
택시 기사가 길은 알아서 가되 목적지는 확인하는 것과 같다.

## 1. 먼저 읽는다

요청(`$ARGUMENTS`)과 함께 있는 것을 먼저 본다: `CONTEXT.md`, `docs/spec.md`, `docs/adr/`, `docs/lessons-learned.md`,
README, 관련 코드와 테스트. **답이 이미 있으면 묻지 않고 가정으로 적고 근거를 단다.**

## 2. 가정 카드를 보여준다

짧게, 쉬운 말로. 전문 용어는 사용자가 먼저 쓴 것만 쓴다.

```
이해한 목표: <한 문장>
할 일: <사용자가 확인할 수 있는 결과 단위로 2~5개>
하지 않을 것: <범위 밖>
가정:
  1. <가정> (근거: <파일이나 사용자 말>)
  2. <가정> (짐작)
제안: <기술 선택이 있으면 "이렇게 하겠다"와 이유 한 줄>
```

근거 없이 짐작한 가정에는 반드시 "(짐작)"을 붙인다. 사용자가 어디를 봐야 할지 알 수 있게.

## 3. 질문은 0~3개, 비싼 것만

**잘못 짐작하면 되돌리기 비싼 것**만 묻는다. 나머지는 가정으로 두고 진행한다.

| 묻는다 | 묻지 않고 가정·제안 |
|---|---|
| 데이터를 지우거나 바꾸는 방식 (되돌릴 수 있어야 하나) | 파일 구조, 패턴, 라이브러리 |
| 돈, 권한, 개인정보가 걸린 규칙 | 함수·변수 이름, 오류 메시지 문구 |
| 외부에 공개되는 범위나 약속 (다른 팀·사용자가 쓰는 것) | 내부 API 모양, 응답 형식 |
| "완성"의 기준 (무엇이 보이면 끝인가) | 재시도, 캐시, 로깅 같은 구현 세부 |
| 범위 경계가 둘로 갈리는 지점 | 테스트 방식 |

- 질문은 상황으로 묻는다. "멱등성을 보장할까요?"가 아니라 "버튼을 두 번 누르면 두 번 처리돼도 되나요?"
- 선택지를 2~3개 주고, 추천 하나에 표시한다. 선택지 도구(AskUserQuestion)가 있으면 그걸 쓴다.
- 비싼 질문이 없으면 묻지 않는다. "고칠 게 없으면 이대로 시작합니다"로 끝낸다.

## 4. 시작한다

- 답을 받으면 가정 카드를 고쳐 한 번만 다시 보여주고 바로 시작한다. 같은 것을 다시 묻지 않는다.
- 사용자가 "그대로 해", 또는 답이 없는(무인 실행) 경우 가정대로 진행한다.
- 작업을 끝내고 보고할 때 "가정한 것" 목록을 함께 남긴다. 특히 "(짐작)"이었던 것은 사용자가 확인할 수 있게 표시한다.

## 5. 남길 것

- 새 용어가 나왔으면 `CONTEXT.md`에 추가한다.
- 되돌리기 어려운 결정(데이터 삭제 방식, 외부 계약)을 정했으면 ADR을 제안한다.

## 하지 말 것

- 모든 분기가 정해질 때까지 묻기, "됐어"라고 할 때까지 코드를 미루기
- 기술 선택(패턴, 라이브러리, 구조)을 사용자에게 넘기기
- 읽으면 알 수 있는 것을 묻기, 한 번 답한 것을 다시 묻기
- 3개를 넘는 질문. 더 필요해 보이면 그건 큰 설계라는 신호다. `/harness-core:domain-interview`를 제안한다
