# 모순 검출 패턴 (Contradiction Detection)
#
# 인터뷰의 본질은 "설문"이 아니라 "모순 잡기"다.
# 매 답변을 받을 때마다, 이미 채워진 슬롯 전체와 교차 검증한다.
# 이 파일은 자주 발생하는 모순 유형과 검출 신호를 정리한 체크리스트다.

## 모순의 3가지 유형

### 1. 직접 충돌 (Direct conflict)
두 답변이 명시적으로 양립 불가능한 경우.
- data_model "주문은 사용자 1명에 귀속" ↔ api_contract 응답에 `shared_user_ids[]` 존재
- data_model "삭제는 소프트삭제" ↔ api_contract `DELETE`가 물리삭제 명시
- auth_flow "stateless JWT" ↔ "관리자가 특정 사용자 세션을 즉시 무효화" 요구

### 2. 슬롯 간 암묵 모순 (Implicit cross-slot)
각각은 말이 되지만 함께 두면 깨지는 경우. 가장 놓치기 쉽다.
- error_handling에 retry 있음 ↔ api_contract에 idempotency 키 없음 → 중복 실행 위험
- edge_cases "동시 수정 허용" ↔ data_model에 버전/락 필드 없음 → lost update
- auth_flow "JWT 만료 24h" ↔ 권한 변경이 즉시 반영돼야 한다는 요구 → 최대 24h 지연
- external_deps "외부 API 비용 호출당 과금" ↔ error_handling "무제한 재시도" → 비용 폭발

### 3. 미명시로 인한 잠재 모순 (Underspecified)
답이 비어 있어서 나중에 충돌이 생길 자리. open_question으로 기록한다.
- 동시성 정책 미정인데 data_model에 카운터/잔액 같은 누적 필드 존재
- 페이지네이션 한계 미정인데 응답이 리스트 반환
- 외부 서비스 장애 fallback 미정

## Phase 0 전용: 도메인 경계 모순
도메인을 발견하고 경계를 그을 때(Phase 0)는 위 3유형에 더해 아래를 점검한다.
경계가 틀리면 그 뒤 모든 슬롯 인터뷰가 어긋나므로 가장 먼저, 가장 엄격하게 본다.
- 책임 중복: 같은 행위가 두 도메인에 동시에 있음 (예: 재고 차감이 '상품'과 '주문' 양쪽에)
- 공유 개념 불일치: 한 개념이 도메인마다 다르게 정의됨 (예: '사용자'가 로그인에선 인증주체, 주문에선 결제주체 — 소유 도메인을 명확히)
- 순환 의존: A→B인데 B→A도 존재 → 그 자리에서 의존 방향을 끊을 방법을 되묻기
- 과대/과소 분할: 한 도메인이 너무 많은 책임을 지거나, 떼어낼 이유 없는 것을 나눔

## 검출 절차 (매 턴)
1. 방금 받은 답변을 해당 슬롯 필드에 기록
2. 위 3유형 체크리스트로 기존 슬롯 전체와 대조
3. 충돌 발견 시 → 그 자리에서 즉시 양자택일로 되묻기 (나중에 몰아 묻지 않음)
4. 잠재 모순 → open_questions에 추가, 인터뷰 종료 전 반드시 해소

## 되묻기 문장 형식
충돌은 "어느 쪽이 맞나"를 (a)/(b) 선택지로 제시한다. 모호한 서술형 질문 금지.

> "앞서 [슬롯A]에서 X라고 하셨는데, 방금 [슬롯B]에서 Y라고 하셨습니다.
>  둘은 양립할 수 없습니다. (a) X 유지 (b) Y 유지 — 어느 쪽인가요?"
